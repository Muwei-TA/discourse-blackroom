# BlackRoom 备份、恢复与更新手册

本手册用于 `https://discourse.muwei.xyz`。现场基线日期为 2026-10-09，记录于 2026-10-10 收尾更新；每次操作先复核目标、挂载和版本。备份生成、独立副本、恢复演练及生产恢复是四个不同结果，不能互相代替。

## 保护目标与现状

- 数据恢复点目标（RPO）为 24 小时，依赖每日备份成功；备份失败或 `/vol4` 副本未更新时，实际可用恢复点会更旧。
- 恢复时间（RTO）以隔离演练实测为依据，不承诺固定时长。NAS 损坏后重新准备硬件、导入镜像、传输数据和恢复入口的时间另计。
- 已配置每日备份，保留 14 份，并包含上传文件。默认备份时刻为 UTC 03:30，即北京时间 11:30。完成时间受任务队列和数据量影响，不能把配置时刻当成备份成功时刻。
- 全部备份存放在 NAS：生产原生备份位于 `/vol1` 的 shared 目录，恢复集合和日常副本集中存入 `/vol4/1000/backup/blackroom`。`findmnt` 已证实 `/vol1` 与 `/vol4` 为不同 btrfs mapper 卷；不同卷仍共用一台 NAS，不是独立设备或地理异地备份，不能覆盖整机丢失等故障。
- `/vol4` 核验时可用空间约 1.6 TB。受保护备份目录权限为 `0700`、文件为 `0600`，其中含数据库、部署凭据和配置，不上传公开仓库或普通聊天附件。Mac 临时备份副本与备份 LaunchAgent 均已移除，不再以 Mac 作为备份目标。

## 一套可恢复材料应包含什么

1. Discourse 原生完整备份：数据库与上传文件，记录完成时间、文件名、大小和 SHA-256，并检查压缩归档可读及确实含上传文件。归档可读不等于数据库可恢复。
2. 同期程序镜像：保存镜像制品并记录镜像 ID、CPU 架构和校验值。`docker commit --pause=false` 只保留容器可写层，不包含挂载卷，也不是数据库一致性快照；程序镜像必须与原生数据备份配套。
3. 实际部署材料：`containers/app.yml`、launcher、templates、自定义插件、Resend 说明、`acg-daily`、crontab 和相关 state。原样副本保存在受保护目录，文档只记录路径与校验结果。
4. 实际运行版本：容器内 Discourse commit、插件版本及本地未提交补丁、镜像 ID、挂载清单、部署配置校验值。仅记录本机仓库 commit 不足以证明生产版本；被 Git 忽略的 `discourse-resend` 必须单独保存并校验。
5. 不同卷副本：先传到临时文件，传完校验一致再作为有效副本；不把未完成下载或零字节文件计入恢复点。保留最后一个校验通过的副本，不能因为源端清理或同步失败就删除它。

每次更新前另建带时间戳的完整恢复集合，保留到更新验收结束且新的备份与独立副本均验证成功。日常 14 份轮换不能替代对这套更新前材料的保留。

## 日常检查

检查最近一次**成功完成**的备份时间、大小趋势、包含上传文件设置、NAS 剩余空间，以及 `/vol4` 最后成功复制时间和校验结果。RPO 目标为 24 小时；监测使用 26 小时无成功备份作为异常阈值，为备份执行留出余量，不代表将目标改为 26 小时。副本落后时记录实际可用恢复点。

NAS 用户 `muwei` 的 crontab 已安装 `blackroom-resilience` 标记任务，`10 * * * *` 每小时第 10 分钟运行，通过 `flock` 防止重叠，调用 `/usr/bin/python3 /home/muwei/discourse-docker-preview/resilience/check_blackroom_resilience.py`。源码为 [检查脚本](../../script/check_blackroom_resilience.py)，状态与日志分别在 `/vol4/1000/backup/blackroom/status.json` 和 `check.log`。先检查状态时间戳，旧的 `errors=[]` 不代表当前正常。

脚本检查目标卷已挂载且不同于 `/vol1`、最新备份及归档完整性、复制后校验、容器/PG/Redis/Sidekiq 进程和 HTTP 状态；异常阈值包括备份超过 26 小时、`/vol1` 使用率达到 90%、`/vol4` 剩余不足 10 GiB。`/vol4` 历史版本不自动删除，需根据空间与恢复点保留需求另行维护。源站 `srvstatus` 和公网入口返回 200 只说明这些检查通过，不能替代登录、帖子及图片业务验收。

当前聊天另有每 6 小时的 Codex heartbeat（ID `blackroom`），补充检查并报告异常；它依赖 Mac/Codex 可用，不是独立报警服务，也不在 Mac 存储备份。NAS 定时检查在 NAS 执行，不依赖 Mac 常开。

检查失败先保留错误日志；重试前排查磁盘空间、运行任务、权限与连通性。不能删除唯一有效备份腾空间，不能把“计划已安装”报告为“每天执行已验证”。同步任务的名称、日志路径与首次运行结果见文末交付记录。

下列命令只读取必要标识；先确认 context 指向预期 NAS：

```sh
docker context ls
docker --context nas ps --filter name='^/app$' --format '{{.ID}}\t{{.Names}}\t{{.Image}}\t{{.Status}}'
docker --context nas inspect --format '{{.Id}} {{.Image}}' app
docker --context nas inspect --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}' app
docker --context nas exec -u discourse app bash -lc 'cd /var/www/discourse && git rev-parse HEAD'
```

不要输出完整 `docker inspect`、环境变量、部署 YAML 或 launcher tracing。需要日志时先在受保护位置保存，再仅摘录无凭据、验证码及私有内容的错误摘要。

## 故障时先判断恢复哪一层

| 现象 | 首选检查与处理 | 恢复边界 |
| --- | --- | --- |
| 公网跳转登录或访问异常 | 已登录浏览器、Pangolin、源站进程与资源请求 | Pangolin 登录页不等于 Discourse 宕机；不据此恢复数据库 |
| 修改主题、插件或配置后出错 | 对比本次变更、运行版本与已存快照 | 优先定向撤销已定位的变更；启动方式和凭据必须匹配 |
| 代码更新失败，但数据库未迁移 | 核对迁移记录与旧镜像兼容性 | 确认兼容后才考虑程序回退，保留当前数据 |
| 已执行数据库迁移 | 核对新旧 schema 与插件迁移 | 不盲降旧代码；选择前向修复或经授权成套恢复 |
| 数据误删、损坏，或持久盘不可用 | 选择最后一个独立且校验通过的完整恢复集合 | 数据恢复会丢失该恢复点以后的写入，必须明确恢复点和损失窗口 |

停止的 `app-before-resend-20261007` 与生产共用 shared 卷，不是独立备份。它只保存旧邮件切换路径，回退可能恢复到 Mailpit；不能据此宣称已恢复 Resend 或所有业务。任何时候都不得让两个容器同时写生产 shared 卷。

## 隔离恢复演练

演练只能在独立容器和新建数据卷中进行。禁止挂载生产 shared 卷为可写，禁止修改生产数据库、DNS、公网路由或原备份。使用复制出的备份制品，记录来源与校验值。

1. 记录演练起点时间、目标镜像、CPU 架构、独立卷路径与恢复备份。核对可用磁盘容量，包含解压、数据库导入与临时文件空间。
2. **在启动任何原镜像入口前**准备隔离策略：覆盖会启动全部服务的默认入口，禁止公网网络出口和对生产服务的连接，不启动 cron、Sidekiq 或其他外部定时任务。复制出的配置清除可用外部凭据，邮件全禁用；网络隔离是额外保障，不能只依赖站点邮件开关。
3. 使用无出口环境导入原生备份。若 `--network none` 用于恢复阶段，它同时阻止普通浏览器访问；需页面验收时另设经验证无出口的隔离网络和仅本机可达的入口，不把演练实例公开到局域网或公网。浏览器也须避免恢复页面触发真实第三方服务，使用隔离配置并检查网络请求。
4. 在演练实例中使用原生恢复流程，只对演练库允许恢复。本次独立空库先运行 `/usr/local/bin/create_db`，再以正确应用身份执行 `rake db:migrate db:seed` 初始化所需扩展，随后 `discourse enable_restore` 并调用原生 restore。只对 `schema=public` 的 dump 直接 `psql` 导入会缺少 `halfvec` 等扩展，不作为复用流程。恢复后重新核对邮件禁用、外部集成禁用和任务停止状态，因为备份会带回站点设置。保留恢复日志与耗时。
5. 对照原记录核对用户、帖子、群组、分区、权限及上传引用的数量或校验信息，不在报告中输出私有帖子正文或成员清单。检查实际上传文件可读。
6. 启动页面所需服务，核验以下验收表。若需要临时管理员或合成社团用户，仅在演练库建立并标注；真实用户密码或验证码由用户自行输入，不记录到日志。
7. 记录恢复结束时间和各验收项结论。停下演练服务，保留日志、版本和结果；清理仅限本次演练创建、已无用途且已识别的资源，不删除备份与回滚材料。

| 验收项 | 必需证据 |
| --- | --- |
| 数据库恢复 | 原生恢复成功、服务启动、基本数据与记录相符 |
| 页面与登录 | 浏览器可登录并实际打开站点；合成账号登录与真实成员登录分别记录 |
| 帖子与图片 | 打开代表性主题、图片或附件，检查原图/缩略图、资源请求和 console |
| 社团隔离 | 本社团成员允许、其他社团成员拒绝、非成员拒绝、管理员允许；覆盖查看、发主题和回复 |
| 外部副作用 | 无出口配置有效，真实邮件、cron 与外部后台任务未运行 |

服务端社团矩阵可复用 `script/check_club_isolation.rb`，先核对脚本存在及其事务回滚行为，再以 `discourse` 用户在**演练容器**运行。命令必须填入经核实的演练容器名，不能直接复制生产 `app` 目标。服务端结果不能代替真实成员登录验收；临时用户矩阵通过也不能写成真实学生已验收。

## 生产数据恢复与切回

备份和隔离演练授权不自动包含覆盖生产数据。执行前形成可评审的具体恢复方案：目标容器/卷、选用恢复点、预计丢失写入的时间窗口、停机影响、恢复镜像/插件版本、入口切换方式，以及恢复失败时保留哪些材料。已有明确且覆盖这些对象和影响的授权无需重复询问；目标或损失范围改变则重新确认。

获得具体授权后，进入维护窗口并阻止新写入，停下相关后台任务，保存当前故障现场、数据库和上传文件副本。优先恢复到新卷并验证，保留故障原卷；执行前再次核对源卷与目标卷，防止覆盖错对象。不要把数据库单独恢复到与其不匹配的上传目录。

按演练通过的同版本路径恢复并做验收，确认只有一个实例写目标卷后才切换入口。先验证管理员登录、主题与图片、社团权限，再分项恢复邮件与外部任务。真实邮件仅发送到用户明确指定的对象，并检查实际邮箱和后续操作。失败时停止切换，保留新旧卷和日志；数据库已迁移时不能直接启动旧镜像写新库。

本手册不提供自动覆盖生产的一键恢复命令；具体恢复命令须由本次已核验的镜像、备份和独立目标卷组成。

## 每次更新的最小流程

1. 记录实际生产源码/插件版本、未提交补丁、镜像、配置及挂载；检查本次变更是否涉及迁移、Resend、自定义插件或外部任务。取得所需生产迁移、重启或重大升级的具体授权。
2. 完成更新前原生完整备份及独立副本校验，保存程序镜像和部署材料。先确认 `discourse-resend` 在持久部署源、实际镜像或挂载中的版本一致，不能依赖“本机目录存在”。
3. 在隔离副本验证目标版本及迁移。已执行迁移时，回退预案必须使用兼容 schema 或完整恢复集合；不得假定旧容器可直接接管新库。
4. 按确认的维护窗口执行最小更新。launcher 输出只进入受保护日志；保留旧镜像与恢复材料。更新后核对精确容器、镜像、源码、插件、进程及资源。
5. 在实际公网已登录浏览器验收站点、登录、代表性帖子/图片和相应业务；权限变更执行社团矩阵，邮件变更完成真实邮件链路。仅 HTTP 200 或配置回读不足以判定更新完成。
6. 更新验收通过后核对下一次备份及独立副本；符合 [更新助手发布契约](blackroom-updates-bot.md) 的站点功能更新按契约发布。单纯备份、隔离演练和失败部署不冒充功能上线。
